# Kickoff: first three weeks, and exactly what to give Codex

Read `PRD.md` and `AGENTS.md` first. `config/sources.yaml` has the verified source findings.

The governing rule for everything below: **Codex writes parsers well only when it can see the
real document.** Every parser task must ship with a downloaded fixture already in the repo. A
parser written against an imagined PDF layout produces plausible code that fails on contact
with reality, and you will not notice for two weeks.

---

## Week 1 — no code

### Days 1–2: lead-time feasibility test

Delegable to a web-capable agent. Spreadsheet output. This gates everything else.

The lookups are search-and-record and should be automated. What stays with you is the
decision at the end, because "is an 11-of-20 hit rate good enough to spend two months on"
is a business judgement, not a task.

Pick 20 Indian deeptech companies that raised a seed round in the last 18 months. Weight
toward bio, medtech, defence and materials, since that is where the grant sources are
strongest. For each, search:

- BIRAC BIG awardee PDFs (BIG-16 through BIG-24 are on birac.nic.in)
- The partner incubator sites named in the BIG reference prefixes
- InPASS, manually, for a patent filing under the company or founder name
- The incubator portfolio page for whichever institution the founders came from

Record: company, seed date, earliest alt-data appearance, source, **lead time in months**.

| Result | Action |
|---|---|
| 15+ of 20 with meaningful lead | Premise validated, proceed as planned |
| 8–14 | Proceed, but cut the source list to whatever actually hit |
| Under 8 | Stop. Rethink the premise before spending two months on it. |

Also record how many of the 20 appear as **individual persons** in a grant list before the
company existed. That number sizes the watchlist feature, which is the differentiated part.

### Days 3–5: hand-download the fixtures

Delegate this, but not to Codex. Codex's sandbox has restricted network egress and will not
reach `birac.nic.in` or `mcacdm.nic.in`. Use a web-capable agent (Claude with web fetch, or
Claude in Chrome) to pull the artifacts, then commit them into the repo so Codex can see them
locally. Verified working: `birac.nic.in` PDFs fetch and text-extract cleanly.

**The one thing that cannot be outsourced end-to-end is accepting the expected output**, and
the reason is circularity rather than effort. If the same model reads the PDF, writes
`expected.json`, and then writes the parser to match, the test proves only that the parser
agrees with the model's reading. A misread — a wrapped company name truncated, a category
header swallowed, a row silently dropped — passes green and corrupts the dataset permanently.
The golden fixture is the ground truth for every downstream decision, so it cannot be
generated by the thing it is supposed to check.

The non-circular version, all of it delegable:

1. Agent A (web-capable) fetches the PDF and produces `expected.json`, in its own session.
2. Agent B (Codex) writes the parser against the committed PDF, with no access to
   `expected.json` while writing.
3. Independently, assert invariants that don't depend on either reading: row count matches the
   printed table totals, every reference number matches
   `BIRAC/[A-Z]+\d+/BIG-\d+/\d+`, every incubator prefix is in `config/incubators.yaml`,
   no applicant name is empty or ends in a dangling legal-suffix fragment.
4. You spot-check five rows against the rendered PDF. Five, not fifty-one. Two minutes.

Step 3 is what actually catches the failures, and it's fully automatable. Step 4 exists
because you're the one who pays if the data is wrong.

1. `BIG-24` awardee PDF and `BIG-21` awardee PDF (deliberately two cohorts — the layouts
   differ, one has a score column and one does not, which is the whole point)
2. One MCA Company Master Data export, filtered to Karnataka + a manufacturing or business
   services classification. **Check the snapshot date.** If it still says June 2025, that is
   a material finding and the watchlist design changes.
3. One Patent Office Journal weekly PDF
4. The NIDHI TBI list page

Save into `src/connectors/<key>/fixtures/`. Confirm each opens and contains what
`sources.yaml` claims. Update `verified:` flags as you go.

## Week 2–3 — the Codex sequence

Give Codex `PRD.md`, `AGENTS.md` and `config/sources.yaml` as persistent context in every
session. Then work through these in order. Do not reorder. Do not parallelise until step 6.

---

### Prompt 1 — scaffold only

> Read PRD.md, AGENTS.md and config/sources.yaml.
>
> Create the repository skeleton described in the AGENTS.md "Repository layout" section.
> Directories, `__init__.py` files, empty modules with docstrings stating each module's
> responsibility, a `pyproject.toml` using uv, a `Makefile` with `test`, `lint` and `run`
> targets (for CI and macOS only — `uv run pytest` is the canonical command on Windows),
> a `conftest.py` that blocks all network access during tests, and a `.gitignore`.
>
> Write no business logic. No parsers, no models, no scoring. Structure only.
>
> Then populate `docs/DECISIONS.md`, which is currently an empty placeholder. Write one entry
> per architectural decision already fixed, each stating the decision, the reason, and what
> would have to change to reverse it.
>
> Source them from two places and do not miss any: PRD.md section 6 and the "Key design
> decisions" note beneath it, plus every "Decisions promoted to docs/DECISIONS.md" block in
> PROGRESS.md. As of now that set includes: append-only signals; immutable raw docs; dual
> Person/Company spine; tenant_id on tenant-scoped tables only; connectors never touching the
> database or setting company_id; patents as a depth signal rather than a detection signal due
> to the 18-month s.11A lag; the LLM cache key being
> (content_hash, extractor_version, prompt_version); L3 Enrich being a distinct budget-gated
> layer that must not be collapsed; grant awardee lists being provisional; and applicant type
> resolving to five classes rather than two.

Review this yourself. Fix the layout now, while it costs nothing.

---

### Prompt 2 — schema

> Implement `src/core/models.py` using SQLModel, matching PRD.md section 6 exactly, including
> the dual Person/Company spine described in the correction note.
>
> Add the `watchlist` concept: a table tracking individual grant awardees who have no
> associated company yet, with the awarding signal, the person, and a status.
>
> Generate the initial Alembic migration. Include `tenant_id` on the tenant-scoped tables
> (`score`, `review_event`) even though there will be one tenant. The `tenant` table itself
> does not carry `tenant_id`; its own `id` is the identity.
>
> Add `tests/test_models.py` asserting the invariants in the AGENTS.md "Data model invariants"
> section are enforceable: that signals carry provenance, that raw_doc has a unique content
> hash, that signal.company_id is nullable.

---

### Prompt 3 — storage layer

> Implement `src/core/storage.py`. It owns all outbound HTTP and all raw document persistence.
>
> Requirements: a `fetch()` helper enforcing one request per two seconds per domain, a real
> user agent with a contact address, robots.txt checking, retries with backoff, and content
> hashing. Fetched bytes are written to disk and a `raw_doc` row is created. Re-fetching
> identical content must not create a duplicate row.
>
> Also implement `src/core/provenance.py` with a helper that constructs a Signal and raises if
> any provenance field is missing.
>
> Add `tests/test_contracts.py` with a test that iterates every registered connector and fails
> the build if any returned signal lacks source_url, retrieved_at, raw_doc_id or
> extractor_version. It should pass trivially now with zero connectors registered.

This is the module everything else depends on. Read it line by line before moving on.

---

### Prompt 4 — the connector contract

> Implement `src/connectors/base.py`: the `Connector` ABC exactly as specified in AGENTS.md,
> plus `FetchTarget`, a registry that discovers connector subclasses, and the orchestrator
> that calls discover, fetches via core.storage, calls parse, and persists signals.
>
> The orchestrator must catch exceptions at the per-connector boundary, record the failure in
> `source.health_status`, and continue with remaining connectors. One broken source never
> stops a run.

Review this one hardest. Everything downstream inherits its mistakes.

---

### Prompt 5 — first real connector

Confirm the BIG PDFs are actually sitting in the fixtures directory before sending this.

> Implement `src/connectors/birac_big/`.
>
> Two golden fixtures are already present: `big_24.pdf` and `big_21.pdf`. Their layouts
> differ — BIG-21 has a final-score column, BIG-24 does not. Handle both.
>
> Write the tests first. Hand-check a few rows from each PDF, encode them as
> `big_24.expected.json` and `big_21.expected.json`, confirm the tests fail, then implement
> `parse()` until they pass.
>
> Parse the proposal reference number into its components. The middle segment identifies the
> partner incubator: CCAMP, FITT, SINE, IKP, VENTURE, SIIC, KIIT, NAARM. Put that mapping in
> `config/incubators.yaml`, do not hardcode it.
>
> Critically: applicant names are sometimes companies and sometimes individual persons
> ("Mr. Davinder Siwal", "CrisprBits Private Limited", "Sujatha.M"). Emit a different signal
> type for each case. Do not attempt to guess a company for a person. Classify conservatively
> and route anything ambiguous to review.
>
> `discover()` must scrape the cohort listing pages rather than constructing URLs. The
> download paths are unix-timestamp prefixed and not guessable.
>
> Observed hazards in the real BIG-24 text extraction. Every one of these must have a test:
>
> - **Company names wrap across lines.** "Nilico Green Technologies Private \nLimited",
>   "Bionano Integra Healthcare OPC \nPrivate Limited", "Shree Veerabhadreshwara Solutions
>   \nLLP". A line-oriented parser silently truncates these. Rejoin continuation lines before
>   field assignment.
> - **Row numbering changes layout mid-table.** In the Medical Devices section, rows 1–13 put
>   the serial number on its own line; rows 14–20 put it inline with the reference number.
>   Do not anchor on line position.
> - **Header punctuation is inconsistent.** "S. No." and "S.No." both appear. "Category -"
>   uses a hyphen in three sections and an en dash ("Category –") in the fourth. Normalise
>   dashes and whitespace before matching headers.
> - **Applicant type has five classes, not two.** Private Limited, LLP, OPC Private Limited,
>   individual person (honorific-prefixed), and genuinely ambiguous bare names with no legal
>   suffix and no honorific ("Trish-I", "BacAlt BioSciences"). Emit the ambiguous class as its
>   own signal type routed to review. Do not force it into company or person.
> - **The list is provisional.** BIG-24 carries the footnote that awards are subject to
>   further due diligence and budget availability. Capture that as a `provisional` flag on the
>   signal and discount it in scoring. An announced awardee is not a funded awardee.
>
> BIG-24 contains 51 awardees across four categories (20 / 8 / 15 / 8). Use those section
> totals as a row-count assertion.

### Prompt 6 — review app skeleton

> Build `src/surfaces/app.py`, a Streamlit review queue with the triage view from PRD section
> 9. One company or person at a time, all signals with dates and clickable source links, and
> four keyboard-driven actions writing to `review_event`: interesting, not for us, already
> known, data is wrong.
>
> No scoring yet. Order by most recent signal.

Stop here and use it for an hour against real BIRAC data. This is where you find out whether
the schema actually supports the workflow. Fixing it now is an afternoon; fixing it after ten
connectors is not.

---

### After step 6, fan out

Now parallelise. Each connector is an independent task referencing `birac_big` as the sibling
example. Suggested order, based on the audit:

1. `mca_company_master` — the spine, plus the freshness verification
2. `patent_office_journal` — hardest parser, start it early
3. `nidhi_tbi_list` — the meta-source that makes the DST fan-out tractable
4. `idex` — needs manual site inspection first to find whether a listing exists
5. Individual institutional incubators, seeded from the TBI list

Entity resolution (`src/resolve/`) comes after the spine lands, and you should write the
blocking and feature logic yourself. Hand Codex the implementation and the tests, not the
design. Resolution quality caps everything downstream and it is the wrong place to delegate
judgement.

## Things that will go wrong, and the tell

| Symptom | Cause | Fix |
|---|---|---|
| Parser works on the fixture, fails on the next cohort | One fixture per source instead of per cohort | Add a fixture per layout variant |
| Codex invents plausible field names | It never saw the document | Always download first |
| Ten connectors, no review app | Fan-out before the vertical slice | Enforce the step-6 gate |
| Silent empty runs for weeks | No source health surfacing | Health block in the digest from day one |
| Bill spikes on director lookups | Enriching the whole graph | Threshold gate plus hard monthly budget in config |
| Merge decisions feel arbitrary | Thresholds tuned to make tests pass | Never widen a threshold to green a test |
